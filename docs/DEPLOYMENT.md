# GitHub and Render deployment

Prepared October 28, 2026. This is a single Docker web service: Flask serves the React build and API on the same HTTPS origin. Railway MySQL stores account data, login sessions, and request limits. A Render persistent disk stores uploaded photos. No Redis service is needed.

## Publish the source

Use the project folder or the clean `release/gather-gift-source.zip` bundle. The bundle excludes `.env`, local databases, uploads, session files, development mail, dependencies, build output, and test result files. Keep the GitHub repository private while completing acceptance checks.

The project is connected to `SandyJime21/gather-gift` and Git is installed. For a new checkout/repository, the equivalent setup commands are:

```powershell
git init -b main
python scripts/release_check.py
git add .
git diff --cached --name-only
git commit -m "Prepare MVP for Render"
git remote add origin https://github.com/YOUR_ACCOUNT/YOUR_REPOSITORY.git
git push -u origin main
```

Inspect the staged names before committing. Never stage `.env`, `backend/instance`, photos, exported lists, or mail previews. If a real secret was previously committed, remove it from history and rotate it; adding an ignore rule does not remove tracked files. The release script checks tracked files when Git is available and reports filenames without printing credential values.

The workflow `.github/workflows/ci.yml` runs frontend tests/build, backend tests, source checks, an empty MySQL migration and schema comparison, and a Docker build. Require both jobs on pull requests to `main`. Render uses `autoDeployTrigger: checksPass`, so subsequent automatic deployments wait for passing CI. [Render CI integration](https://render.com/docs/deploys#integrating-with-ci).

## Connect Render

1. Provision an empty **managed MySQL 8** database with backups and TLS. The Blueprint does not create a MySQL server; Render's managed Postgres is a different database and cannot substitute for it. Do not point production at the laptop database.
2. In Render, create a Blueprint from the GitHub repository using root `render.yaml`. Review the paid web service and persistent disk before creating them.
3. Supply the required settings below. The Blueprint generates the app secret. Sessions and request limits use the same MySQL connection as the rest of the app.
4. Deploy. The pre-deploy command applies Alembic migrations once; Gunicorn starts the app after migration succeeds. The Docker build includes the frontend; no separate static-site service or frontend API URL is required.
5. Check `/ready` returns `{"status":"ready"}`. In production it checks MySQL, migration head, and the shared session/limit tables. `/health` remains a lightweight liveness endpoint.

The persistent disk is mounted at `/var/data`, with photos at `/var/data/uploads`. Keep this disk across deployments. A service with a persistent disk can have deployment downtime and cannot use the usual multi-instance disk sharing assumptions. Database backups and upload-disk backups are separate. [Render deployment and disk behavior](https://render.com/docs/deploys), [Blueprint fields](https://render.com/docs/blueprint-spec).

| Setting | Value / source |
| --- | --- |
| `APP_ENV` | `production` (Blueprint) |
| `SECRET_KEY` | Generated by Render; keep stable across deploys |
| `DATABASE_URL` | Managed MySQL connection: `mysql+pymysql://USER:URL_ENCODED_PASSWORD@HOST:PORT/DATABASE?charset=utf8mb4` |
| `DATABASE_SSL_CA` | Optional path to your database provider's CA certificate, e.g. a Render secret file at `/etc/secrets/mysql-ca.pem`; default uses trusted public CAs |
| `SESSION_TYPE` | `mysql` (Blueprint; production uses MySQL even if an old Redis setting remains) |
| `RATELIMIT_STORAGE_URI` | `appsql://` (shared MySQL request limits; no separate connection URL required) |
| `UPLOAD_FOLDER` | `/var/data/uploads` (Blueprint) |
| `SMTP_HOST` | Your email provider's SMTP hostname |
| `SMTP_PORT` | `587` |
| `SMTP_STARTTLS` | `true` |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Provider credentials, if required |
| `MAIL_FROM` | Verified sender address accepted by the provider |
| `FRONTEND_ORIGIN` | Omit for the initial `onrender.com` domain: the app uses `RENDER_EXTERNAL_URL`. Set to your exact `https://your-domain.example` origin when adding a custom domain. |

Passwords containing `@`, `:`, `/`, `#`, `%`, or other URL-reserved characters must be URL encoded in `DATABASE_URL`. MySQL certificates and hostname verification are required in production. Put all secrets in Render settings or secret files, never in a `VITE_` variable or the repository. Do not set the local example `RATELIMIT_STORAGE_URI=memory://` on Render.

Production fails early if the origin, secret, managed database configuration is missing/unsafe. Missing email settings do not block startup or database migrations. Password/PIN recovery, verification, and deletion backups remain unavailable until SMTP is configured; deletion stops before removing data if its backup cannot be sent. When SMTP is configured, production requires STARTTLS. Inbox delivery still needs a real test.

## Optional integrations

The Blueprint leaves online shopping search, payments, ad rates, and affiliate tracking disabled initially. Manual wishes and manual profile favorites work without these services; optional Wikipedia favorites search does not require an API key.

- Online product search: set backend `SERPAPI_API_KEY` only when ready to enable it. Child search additionally requires parental approval.
- Payments: set both `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` in **test mode first**. Register `/api/ads/stripe-webhook` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded`, and `charge.dispute.created`. Do not enable live mode until checkout, webhook, refund, and deleted-family scenarios pass end to end.
- Advertising: set the desired `ADS_*_DAILY_RATE_CENTS` values before approving paid campaigns.
- Affiliate rules are optional. No tracking ID is required to launch the registry.

For optional settings managed as `value:` entries in `render.yaml`, update the Blueprint too when enabling them; later Blueprint syncs can reapply its declared values. Do not put actual secret values in the YAML: change a secret's entry to `sync: false` and set its value in Render.

Letter-art purchases unlock once per family. If a pending checkout is paid after the family disappears, the signed webhook requests a full refund with a stable idempotency key; failures return a retryable status. Previously fulfilled purchases are not refunded merely because their family was later deleted. Minimal one-way payment receipt hashes distinguish retries without retaining deleted family/buyer details. [Stripe refund API](https://docs.stripe.com/api/refunds/create).

## Developer portal

In the deployed service's Render Shell, create the initial developer account:

```sh
flask --app backend create-superuser
```

Enter the developer email/name and a unique password of at least 16 characters when prompted. This command refuses to create a second master account or reuse an existing family-account email. Sign in at `/support/login`. Use the portal to invite staff, manage support, review advertising requests, confirm the advertising notification recipient, manage artwork/themes and free/paid letter designs, and review transaction reports. No default developer login is shipped.

## Before inviting families

- Confirm GitHub's frontend/backend checks and image build are green.
- Register/sign in, refresh the page, sign out, and confirm the active user's own header photo.
- Create a family, child, and pet; upload photos and confirm they survive a redeploy. Photos on the laptop do not migrate automatically: move any existing database/uploads together through a deliberate data migration.
- Test a follower account, private/public lists, gifts, budget filters, and profile preferences on desktop, phone, and iPad.
- Enter child mode: only approved wishlists/manual wishes should appear initially. Test each parental switch and immediate server-side revocation; verify adult settings/payments remain blocked and PIN exit works.
- Verify invitation, password/PIN recovery, advertising alerts, and deletion CSV delivery in real inboxes. Use disposable test families for deletion/ownership transfer.
- Test Stripe in test mode if enabling paid features; keep live payments disabled until acceptance passes.
- Configure backup/restore procedures for MySQL and uploaded files.

Use `flask --app backend db upgrade` for existing databases. `schema.sql` is now regenerated through `2cd69e815ba3`, but its administrator/bootstrap passwords are **local development examples only**. Do not run it, or the fake demo-data `mysql.sql`, against production.

## Update an existing Blueprint without starting over

Keep the existing web service and its upload disk. Deploy the latest commit so the pre-deploy migration creates `app_session` and `request_limit`. The code does not use Redis in production, even if old `SESSION_TYPE=redis` or `REDIS_URL` values remain temporarily.

Sync the existing Blueprint with the updated `render.yaml`; do not create a duplicate Blueprint. Review any removal prompt carefully: only `gather-gift-redis` is obsolete. Keep `gather-gift` and its upload disk. After the web service is healthy and sign-in works, delete the unused Redis/Key Value service if Render has left it in place. Remove its old `REDIS_URL` variable too. Never delete the web service, upload disk, or Railway database for this change.

Existing logins will expire once when switching storage; users sign in again. No accounts, wishes, or photos are deleted. Expired state is cleaned automatically on roughly one in 100 requests. MySQL counters use atomic fixed-window updates shared across workers and fail closed when the database is unavailable. This adds some MySQL traffic and is appropriate for the current MVP; it avoids a separate Redis service.

## Current verification limits

Source changes are pushed to GitHub; Render deployment status must be checked in the Render dashboard. The local Docker daemon is unavailable, so the actual container build is assigned to GitHub CI. Managed-MySQL TLS, deployed database/network access, SMTP inbox delivery, Stripe test-mode round trips, and real device acceptance depend on the configured deployment and cannot be certified by local unit tests.
